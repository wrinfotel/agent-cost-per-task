# agent-cost-per-task

What does one **successfully completed** task actually cost a coding agent?

Not the price per call. Not the price per token. The number that matters when you
decide whether to keep using an agent: **total spend on all attempts — including the
failed ones — divided by the number of tasks that met a success criterion defined in
advance.**

This repo is a small, reproducible way to measure that on your own logs.

## Definitions (read these first)

- **Attempt** — one agent run from start until it stops (or is stopped).
- **Outcome** — `success` or `fail`, judged by *your* pre-registered criterion
  (tests green, review passed, spec item done). Not "looks good to me".
- **Cost per attempt** — total measured cost / number of attempts.
- **Cost per successful task** — total measured cost / number of tasks that succeeded.
  Failures and retries are included in the numerator on purpose.
- **Retry tax** — share of total spend burned by attempts that did not lead anywhere.
- **Cache share** — cached input tokens as a share of all input tokens.

If zero tasks succeed, cost per successful task is **undefined**. The script says so
instead of dividing by zero.

## Quickstart

```bash
python3 parse.py sample.csv                    # demo data, 12 tasks
python3 parse.py mylog.csv --out report.csv    # your log
python3 parse.py mylog.csv --review-rate 25    # add $25/h of manual review to the total
```

Input CSV columns:

```
task_id,outcome,attempt_no,input_tokens,cached_tokens,output_tokens,tool_calls,duration_min,cost_usd
```

One row per attempt. Several rows may share a `task_id`. Leave `cost_usd` empty when
the cost is unknown — the script warns you rather than silently treating it as a fact.

## What is NOT counted

- Subscription fees (flat monthly plans) are **not** converted into per-token costs.
  If you pay a flat fee, say so separately instead of inventing an allocation.
- Infrastructure, electricity, your own machine time — separate line or omit.
- Manual review time is only included when you pass `--review-rate`, and then it is
  labelled as an assumption.
- Tasks that were abandoned mid-flight without a result still count as attempts.

## Limits to publish next to your numbers

Anyone reading your numbers will check exactly this list. Put it in the post:

- one repo, one setup, one model, one time window — **not a benchmark**;
- the task set is small and hand-picked; do not generalise it;
- "success" is a judgement: the criterion was fixed before the run, but it is still
  your criterion, and tests plus review are imperfect;
- task boundaries are a judgement call — retry counts depend on where you cut them;
- fewer than 10 solved tasks: publish as a *method*, not as a benchmark.

## Why this exists

Public comparisons usually measure what a model can do once. In practice the bill is
driven by retries, bad tool calls and re-runs — and that cost is invisible in dashboards
that report spend per call.

Background worth reading before trusting any coding benchmark: METR on measuring long
tasks, NIST CAISSI on flaws in agent evaluations, and OpenAI's audit of SWE-bench Pro
(July 2026), which estimates roughly 30% of its tasks are broken.
